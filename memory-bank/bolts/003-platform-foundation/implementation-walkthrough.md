## Implementation Walkthrough: platform-foundation (bolt 003)

### Summary

The app is now an installable PWA that keeps working on a weak connection: pages already visited open offline, a banner says when the device is offline, typed input is kept on the device, and shared loading, empty and error patterns exist. Automated checks guard payload size, speed, accessibility and spacing. The labelled training seed can be validated and loaded with one command that recreates the database.

### Structure Overview

- **PWA layer**: a manifest and icons, a service worker generated by Workbox after the build (static files precached; visited pages cached network-first; admin pages and the language switch never cached; an offline page for pages never opened), and a registration script that only runs in production builds.
- **Connection comfort**: an offline banner (a small island), and a small script that saves and restores form input marked for persistence.
- **Shared states**: three reusable components (loading, empty, error) with message keys in all three catalogs.
- **Performance and accessibility**: fonts limited to the Latin and Bengali subsets; tests that measure payload and interactive time under throttled 4G, scan every route in both languages with axe, and check keyboard order, focus visibility and 8 px spacing.
- **Seed**: five labelled JSON files, a validator that refuses any trust signal, two reference tables, and a runner that recreates the database, loads the data and resets the Dummy services if they are running.

### Key Decisions

- **Visited pages cached network-first with a 3 s timeout**, so a slow network falls back to the last copy instead of waiting.
- **Admin pages are never cached offline**, because they will hold sensitive records and may be opened on shared devices.
- **The offline page is cached when the service worker installs**, in whichever language the visitor had then.
- **Form persistence is opt-in** (`data-persist`), never automatic, and never keeps secrets.
- **Seed scope**: files, validation and the reset-and-load command now; neighbourhoods and vet clinics loaded now; owners, pets, providers and the admin validated now and loaded by the bolts that create their tables.
- **Trust-signal guard by key name** anywhere in the seed (rating, review, testimonial, stars, booking count, completed bookings, verified stays, years hosting, response time), plus strict schemas that reject unknown keys.
- **Seed refuses non-local databases** and unsafe database names.
- **TTI is a documented proxy** (load plus every island hydrated, slow-4G network, 4x CPU slowdown); the full Lighthouse report belongs to workbook Step 32.

### Deviations from Plan

- The config-literal check no longer watches basis-point numbers (1000, 800, 1600): they are everyday numbers in code and caused a false alarm. The config test pins those values instead. It also skips JSON and CSS files.
- The seed provider records avoid numeric experience claims such as "years hosting" (a fabricated trust signal under the same rule).
- Astro starts its development server in the background in this agent environment, so Playwright cannot start it itself; the server is started once beforehand (documented in the test notes). For a normal terminal the configured command works as written.

### Developer Notes

- Build with `npm run build` (runs Astro, then the service worker step); serve the build with `npm run start:web`.
- The service worker is skipped in development; PWA and performance tests run on the production build on port 4322.
- To keep form input across a failed save, give the form `data-persist="a-unique-name"` and dispatch the `pc:persist-clear` event after a successful save.
- `npm run seed` recreates the `petcare` database; any other local work in it is lost.
- Verified by hand while building: the production build precaches 21 files (244 KB) and ships only Latin and Bengali fonts; the seed run shows 3 neighbourhoods, 6 clinics and the validated counts.
