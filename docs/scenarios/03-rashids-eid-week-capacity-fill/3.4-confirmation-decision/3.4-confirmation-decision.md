# 3.4 — Booking Confirmation Decision

## Overview

**Page Purpose:** Capture Rashid's accept/decline decision with structured decline reasons when applicable — so the platform captures routing data for future matching improvements.

**Entry Context:** Rashid tapped Accept or Decline on 3.3.

**Exit Action:** Accept → returns to 3.1 with booking in "Confirmed" column · Decline → returns to 3.1 with booking removed + decline reason logged.

## Page Composition (Accept path)

### Confirmation modal
- "Accept Tito's stay, Eid-1 → Eid+9?"
- **Summary:** 9 nights · BDT 19,800 · insulin BID
- **Confirm CTA**
- **Helper:** "Capture-on-confirmation: Bibi's payment will be charged"

### After accept
- "Booking confirmed · Bibi notified"
- Booking moves to Confirmed column

## Page Composition (Decline path)

### Structured decline reasons (taxonomy from Brief §3)
1. Cannot administer medication
2. Cannot accommodate high-anxiety pets
3. Cannot support senior / limited-mobility pets
4. Care requirements exceed capacity
5. Facility / environment not suitable
6. Generic decline (with free-text required)

### Each reason → optional free-text elaboration
- Helps the routing-data layer (Brief §2: structured decline reasons are first-class)

## State Variations

- **Accept-success**: Booking moves to Confirmed · capture-on-confirmation fires
- **Decline-with-reason**: Decline reason logged · routing-data updated · Ayaat's queue shows the decline for monitoring
- **Decline-without-reason**: Forced to pick a reason (taxonomy enforced)

## What This Page Must NOT Do
- No counter-offers (Brief §6 explicit non-goal — accept-or-decline only in v1)
- No "negotiate price" path
- No "discuss with owner first" chat before deciding — the structured care config is meant to be sufficient
